# agent-harness

## ADDED Requirements

### Requirement: Every repository carries a complete, self-contained harness

An agent opened on a single repository SHALL have everything it needs to work: no
sibling repository, no global store, no machine-specific configuration, and **no
harness content fetched at run time** — skills, hooks, templates, agents and
commands are all committed.

The network remains necessary for what the network legitimately owns: restoring
packages, downloading the SDK during `setup-env`, and querying advisory databases.
Self-containment is about the harness, not about isolation from nuget.org.

Seventeen skills SHALL be committed in each repository, physically duplicated in
`.agents/skills/` and `.claude/skills/`.

The set SHALL be exactly: `ask-matt`, `improve-codebase-architecture`,
`setup-matt-pocock-skills`, `setup-pre-commit`, `to-questionnaire`, `to-spec`,
`to-tickets`, `triage`, `wait-what`, `writing-for-agents`, `tdd`, `code-review`,
`verification-before-completion`, `using-git-worktrees`, `diagnosing-bugs`,
`resolving-merge-conflicts`, `finishing-a-development-branch`.

Content SHALL come from the public upstream and SHALL be committed, never fetched
at run time. A repository-local command SHALL refresh them from upstream **and
commit the result**, so an update is a reviewable pull request rather than a silent
mutation. Symbolic links SHALL NOT be used: without
Developer Mode, a Windows checkout degrades them into text files containing the
target path.

#### Scenario: a repository cloned alone is fully operational
- **GIVEN** a fresh clone of any repository, with no other repository present
- **WHEN** an agent runs `./scripts/setup-env.sh --check`
- **THEN** it reports readiness or names precisely what is missing

### Requirement: Every repository declares its agent entry points

A repository SHALL carry, at its root, an entry point for **each** agent family, so
that no agent depends on another's configuration:

| File | Purpose |
|---|---|
| `CLAUDE.md` | Claude Code entry point — objective, layer, invariants, commands |
| `AGENTS.md` | Codex and cross-agent entry point, carrying the same content |
| `.claude/settings.json` | permissions, hooks, status line, environment |
| `.claude/agents/`, `.claude/commands/` | the repository's domain reviewers and commands |
| `.agents/skills/`, `.claude/skills/` | the seventeen vendored skills |

`CLAUDE.md` and `AGENTS.md` SHALL stay in agreement; a check SHALL fail the build if
their shared sections diverge. The previous ecosystem had no `AGENTS.md` anywhere,
leaving Codex with no entry point at all.

#### Scenario: an agent opened on a bare clone knows where it is
- **GIVEN** a fresh clone opened by any agent family
- **WHEN** the agent reads its own entry point
- **THEN** it finds the repository's layer, its invariants, its script verbs, and
  the constraint that its wrapper may reference only its binding

### Requirement: Agent hooks enforce what prose cannot

`.claude/settings.json` SHALL configure, at minimum:

- **`PreToolUse`** — refusing edits when `master` or `develop` is checked out, and
  running the credential detector before any write. The pattern SHALL name the
  branches this flow actually produces: there is no `release/*` branch, Release
  Please working on its own `release-please--*` branches, and a deny rule naming a
  branch the flow never creates is precisely the dead rule this requirement forbids.
- **`PostToolUse`** — running the formatter on written files.
- **`Stop`** — printing the pre-pull-request gate: tests run, coverage met,
  specification validated.

Hooks SHALL be committed, identical across repositories, and delivered by the
template. Deny rules SHALL name branches that actually exist in the repository; a
dead rule SHALL be reported by the ecosystem audit.

#### Scenario: an agent cannot edit a protected branch
- **GIVEN** an agent working with `develop` checked out
- **WHEN** it attempts to write a source file
- **THEN** the `PreToolUse` hook refuses the write and states that a feature branch
  and a worktree are required

### Requirement: The harness comes from a generated template, never synchronised

`Rinzler78.Templates` SHALL publish `dotnet new` templates that expand a complete
harness into a new repository. A generated repository SHALL NOT reference its
source. `Meta` SHALL hold no templates and SHALL NOT push into sibling repositories.

Drift SHALL be reported by a non-blocking job that compares the recorded template
version against the published one. Updating remains a deliberate pull request in
the repository concerned.

#### Scenario: the template bootstraps itself
- **GIVEN** the `Rinzler78.Toolkit` repository
- **WHEN** its own harness is regenerated by its own template
- **THEN** the result is byte-identical to the committed harness

### Requirement: The template separates what it owns from what it seeds

A template expands two kinds of file, and conflating them makes the byte-identity
check either impossible or dishonest.

**Harness** files are owned by the template for the lifetime of the repository:
scripts, hooks, agent hook configuration, the pre-commit configuration, the
workflows, the issue forms, the labels, the toolchain manifests and the ignore
rules. A repository SHALL NOT edit them; divergence is a defect and the check SHALL
fail on it. Extension SHALL happen by convention rather than by editing: a
repository adds a check by adding a script to `scripts/hooks/`, which the runners
discover, so the configuration that runs them stays byte-identical everywhere.

**Seed** files are expanded once and then belong to the repository: the `README.md`,
the two agent entry points, the solution file, the central package versions, the
spelling dictionary and the project scaffold. Their content is repository-specific
by construction — a README that could not be edited would describe nothing. The
check SHALL assert that each seed exists, and SHALL NOT compare its content.

The template SHALL declare which of its files are seeds, in the template itself, so
that the check reads the distinction rather than restating it. A file the template
ships and does not declare as a seed SHALL be treated as harness.

#### Scenario: an edited harness file fails the check
- **GIVEN** a repository whose `scripts/build.sh` has been modified locally
- **WHEN** the regeneration check runs
- **THEN** it fails, naming that file

#### Scenario: an edited README does not fail the check
- **GIVEN** a repository whose `README.md` has been rewritten for its own subject
- **WHEN** the regeneration check runs
- **THEN** the README is confirmed present and its content is not compared

#### Scenario: a repository-specific check needs no configuration change
- **GIVEN** a repository adding a check that only it needs
- **WHEN** the script is placed in `scripts/hooks/` with its stage declared
- **THEN** both runners execute it, and the pre-commit configuration and the
  workflow are unchanged and still byte-identical to the template's

### Requirement: Three gates, each paying for what it protects

A repository SHALL install three git gates, and each check SHALL declare which one it
belongs to, in its own header, so that one list serves every runner:

| Gate | What it runs | Why there |
|---|---|---|
| `pre-commit` | the fast offline checks, and only the tests the staged change can reach | a commit is part of the loop and SHALL cost seconds |
| `pre-push` | the whole unit suite, the vulnerability and freshness scans, the build contracts | the branch is leaving the machine |
| `pre-merge-commit` | the integration checks and the coverage figure | two histories are becoming one, which is not a loop |

The inventory SHALL be discovered from `scripts/hooks/`, never enumerated a second
time in a configuration file or a workflow. A check that declares no stage, or an
unsupported one, SHALL be refused rather than skipped, and the whole directory SHALL
be validated whatever stage was requested, so that a silent check cannot hide behind
a stage filter. A stage with no check SHALL say so.

Continuous integration SHALL run every stage, so that nothing depends on a developer
having pushed rather than committed.

#### Scenario: a repository-specific check needs no configuration change
- **GIVEN** a repository adding a check that only it needs
- **WHEN** the script is placed in `scripts/hooks/` with its stage declared
- **THEN** both runners execute it, and neither the hook configuration nor the
  workflow changes

#### Scenario: a check with no stage is refused
- **GIVEN** a check script carrying no `# rinzler-stage:` header
- **WHEN** any stage is requested
- **THEN** the run fails, naming the file and the accepted values

### Requirement: The harness survives a template that cannot carry a file mode

`dotnet new` does not preserve the executable bit, and the .NET CLI does not implement
the templating engine's `chmod` post action. A generated repository therefore arrives
with a script facade nobody can execute, and its initial commit would record that for
every clone.

A blocking check SHALL refuse a commit that records a non-executable tracked script,
and `setup-env` SHALL restore the mode. The hook configuration SHALL invoke its
entry through `bash`, so that the check which reports the mode can itself run.

#### Scenario: a generated repository is usable before its first commit
- **GIVEN** a repository freshly expanded from the template
- **WHEN** `./scripts/setup-env.sh` runs
- **THEN** every script under `scripts/` and `.claude/hooks/` is executable

#### Scenario: a non-executable script cannot be committed
- **GIVEN** a script staged with mode `100644`
- **WHEN** the commit gate runs
- **THEN** it fails, naming the file and how to fix the recorded mode
